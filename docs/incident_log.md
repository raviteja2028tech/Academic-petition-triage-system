# Incident log

Only incidents that **actually occurred** while building and testing this project are listed. Nothing is invented for the sake of completeness. Entries from
Phases 0–3 were not kept in a log at the time; the incidents recorded below are from the Phase 4–8 work session (2026-10-28) and were noticed while it ran.
"Impact" is development impact; no production system exists.

| # | When | What happened | Detection | Root cause | Resolution | Prevention |
|---|------|---------------|-----------|-----------|------------|------------|
| 1 | 2026-10-28, Phase 4 | Full test suite slowed from ~48 s to ~130 s after adding metrics to the worker/API | Compared suite timings after the change | Metric writes went to a real Redis on `localhost`, which was not running; each failed write waited for the 2 s connect timeout | Autouse test fixture routes metrics and reliability state to an in-memory fakeredis (`tests/conftest.py`); production code still swallows Redis errors but is bounded by the 2 s timeout | Tests may not touch real network services; the fixture enforces it |
| 2 | 2026-10-28, Phase 4 | Test run failed with `SyntaxError: unterminated string literal` in `api/main.py` | pytest collection error | A `\n` inside a Python string was written into the source as a literal newline by my patch script | Rewrote the line as an f-string | Prefer patch scripts stored as files and run through the interpreter; always run the suite after a patch |
| 3 | 2026-10-28, Phase 6 | Installing OpenTelemetry with pinned 1.41.1 packages downgraded the already installed SDK and produced a pip dependency conflict with `opentelemetry-exporter-otlp-proto-grpc 1.45.1` (another tool in the same Python) | pip output | I pinned versions from memory without checking the installed versions | Re-installed `api`, `sdk`, `exporter-otlp-proto-http` at 1.45.1 so the set is consistent; project requirements pin 1.45.1 | Check installed versions before pinning; use a venv/containers for new tools (pip-audit and Locust were run in a throwaway venv / container) |
| 4 | 2026-10-28, Phase 5 | First scripted evaluation scored 24/28 | The evaluation CLI itself | The scenario expectation was wrong: I assumed unsupported petition types needed no LLM call, but the implemented pipeline makes one triage call, then escalates before retrieval | Corrected the expectation and scripted behaviour to match the implementation (documented in `docs/evaluation.md`); the pipeline was not changed | Expected values come from the specification, then are checked against behaviour; mismatches are investigated before being "fixed" |
| 5 | 2026-10-28, Phase 8 | `pip-audit` reported 5 known vulnerabilities in `chromadb==1.5.9`, including an unauthenticated code-injection issue in the Chroma **server** (CVE-2026-45829) with no fixed version listed | Dependency audit | Upstream advisories against the pinned version | Not fixable from this repository. Mitigations in place: the `chroma` service publishes no port and is reachable only on the internal Compose network; all other published ports are bound to `127.0.0.1`. Residual risk documented in `docs/security_review.md` | Re-run the audit before release; upgrade when a fixed release exists |
| 6 | 2026-10-28, Phase 6 (Docker) | API returned HTTP 500 and the worker crash-looped on first start of the new stack | `docker compose ps` showed the worker restarting; ingest log showed a pydantic float-parsing error | `docker compose` passes unset `PRICE_*_PER_1K` as empty strings; `Optional[float]` rejected `''`. Unit tests never set an empty env var | Settings now treat blank prices as "unknown"; regression test added | Docker run of every new setting before declaring a phase done |
| 7 | 2026-10-28, Phase 6 (Docker) | Jaeger showed API spans but no worker spans | Jaeger service list lacked `triage-worker` | RQ runs each job in a forked process; the batch span exporter thread created in the parent does not exist in the child | `ensure_tracing()` re-creates the provider inside the job process and flushes at job end; verified: one 12-span trace across both services | Same as above |
| 8 | 2026-10-28, Phase 7 | First smoke benchmark: one run took ≈11 s although agents needed ≈2 s; 1-worker throughput 0.05 runs/s in the smoke run (0.067 in the fork-mode benchmark) | Benchmark output and trace timings | Stock RQ forks per job, so the embedding model was reloaded for every petition | Default `WORKER_MODE=simple` (jobs in the long-lived worker, model warmed at start); throughput 0.422 runs/s in the same configuration | Benchmark before optimising; keep `fork` mode switch |
