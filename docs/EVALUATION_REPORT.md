## How to read this

* **Expected** outcomes are the team's reading of the verified corpus (`eval/scenarios.json`); scenarios marked *interp.* depend on the open interpretations in `KNOWN_LIMITATIONS.md` §A (e.g. what "10 %" means), so a pass is technical conformance, not proof of regulatory correctness.
* A **FAIL** means the observed outcome differs from the expectation on at least one of: status, route, escalation reason, whether the LLM was called, citation groundedness, or gold-clause retrieval recall. Expected values were **not** changed to make results pass.
* Each real run is **one sample per scenario** (n = 19). Differences of a scenario or two are not statistically meaningful, and the same model can answer differently on another day.

## Known limitations of this evaluation

* One sample per scenario, two different real models, no human-labelled gold set; regulatory expectations rest on unconfirmed interpretations.
* Runs A and B were not made with identical code: between them the verifier gained a guard that blocks AI *rejections* inside the discretionary band (motivated by Run A's S06/S07, where the model rejected 80 % / 84 % petitions) and the client gained pacing/quota handling. Run B's models did not reject those petitions, so the guard is **verified by unit tests (`test_model_reject_inside_the_condonable_band_is_converted_to_referral`) and scripted scenarios, not by a real-model run**.
* The v1-vs-v2 prompt comparison covers 3 scenarios on one model; the quota prevented more.
* The retrieval metrics count clauses, not passages, and gold clauses are limited to the four verified ones (`docs/corpus_verification.md`).
* LLM-judge scores exist only where the judge call fit the quota (Run A); the judge is an LLM and is not ground truth.
